## What the code reading found (read before Task 1)

- **The API is exactly what CT-b asked for, and it is SwiftUI's.** `TextSelection` (`.indices` is `.selection(Range<String.Index>)` or `.multiSelection(RangeSet<String.Index>)`; `init(range:)`, `init(insertionPoint:)`, `init(ranges:)`) and `TextField`/`TextEditor` with a `selection:` `Binding<TextSelection?>`. There is also a *controlled* spelling beside the binding one (value in, `onSelectionChange:` out), exactly as `onChange:` is the controlled twin of `text:`. The canvas editor already uses the controlled `text:onChange:` spelling because its draft lives in the model, so it uses the controlled selection spelling too, and nothing needs a `Binding`.
- **MetalUI's rules, which this plan relies on (divergences 265, 266; rulings `SL-B`, `SL-D`, `SL-E`, `SL-G`, `SL-H`, `SL-I`).** A selection written before the first frame is applied in that frame and wins over the focus in the same turn (SwiftUI's own `TextField` loses that race; MetalUI's does not). The field publishes its selection after each input that changed it (a press, a drag, a key, ⌘A, a typed commit, undo) and writes nothing at focus or resign. A value the field itself published is never re-applied (its echo is ignored). `nil` is never an instruction. While an input method composes, a write is held back and the commit's publish supersedes it. A stale or out-of-range index is clamped, never trapped, and a multi-selection acts on its first range. A selection write never touches the undo history except to end the open typing group.
- **The model must hold the selection, because the view is rebuilt from it.** `CommentEditorLayer` builds `CommentEditorField` from `model.commentEditor`, keyed by the edit's `owner`; every `commentDraftChanged` rebuilds it with the new draft. If the model did not store what the field publishes, each rebuild would hand the field the *opening* selection again. The field would see a value that differs from the one it last published and would re-apply it, so the second keystroke would replace the title again. `commentSelectionChanged(_:)` stores each publish, and the equality guard (`edit.selection != selection`) makes the echo a no-op.
- **Publish order does not matter.** In one input the field reports the text (`onChange`) and then the selection (`onSelectionChange`); the model's selection is briefly stale against the new draft, and no frame is drawn between the two. `CommentEdit.selectedOffsets` clamps a stale index, and `CommentEditSelectionTests.aStaleSelectionReadsClamped` pins that nothing traps.
- **Ten existing tests encoded MetalUI's old caret-at-the-start** (gap CT-b's own "measured in the C9 probe: `Xhello`"): the typed text went in front of the note. They now expect it after the note's text (`hasSuffix` and `Line one New` where they had `hasPrefix` and `New Line one`). One render test probed a point on the title's text and found the new selection highlight painted over it; it probes the bar's far end instead.
- **Other fields focused from code.** Only the add-node palette's search field (`SearchPaletteView`: `searchFocused = true` on appear) is focused from code besides the comment editor, and it opens with an empty query: there is nothing to select. Every other `TextField` (`TextEntry`, `NumberEntry`, `CommentTitleEntry`, `CommentTextEntry`, `DimensionField`, the theme name) is focused by a click, which places the caret where it landed, or by Tab traversal, where MetalUI already selects all (`SL-F`). CT-b names only the comment editor, so nothing else changes (user decision U3).
- **`TextSelection` is `@available(macOS 15, *)` in MetalUI; the package floor here is macOS 26**, so nothing is gated.
- **A new gap, CT-d.** `MetalUITesting` has no way to compose text (marked text) as an input method does, so the "held back while composing" rule and the model's behaviour around it have no automated test. Human check C25-3 is the cover. It is logged in Task 3 and returned verbatim for the MetalUI session.

## Review Focus

Failure modes the spec implies that a person using the editor would hit, most likely first; each has its test (named) in the owning task.

1. **The title is replaced again by the second keystroke, or the note's caret jumps back.** The view is rebuilt on every keystroke; if the model hands the field the opening selection again the field re-applies it. `CanvasTypingSelectionWindowTests.aTitleOpensWithAllOfItSelectedAndTypingReplacesIt` types a word after the first letter and checks that it appends; `aNoteOpensWithTheCaretAtItsEndAndTypingAppends` does the same for a note (Task 2).
2. **Empty and unusual text must open without a trap or a wrong count:** an empty note, a note ending in a line break (the caret belongs on the empty last line), a title of accented or joined-emoji Characters (offsets are Characters, not bytes). `CommentEditSelectionTests.emptyAndMultiScalarTextOpenWithTheRightSelection`, `aMultiLineNoteOpensOnItsLastLine`; `CanvasTypingSelectionWindowTests.aNoteEndingInALineBreakOpensOnItsEmptyLastLine`, `anEmptyNoteOpensWithTheCaretInIt` (Tasks 1 and 2). The last one is a regression pin only: it passes before the change and would pass if the field ignored the selection (MetalUI's old caret at 0 equals the end of an empty text), so it is not evidence that the opening selection is applied; `aNoteOpensWithTheCaretAtItsEndAndTypingAppends` and the multi-line test are.
3. **A stale selection after the text shrinks (undo, paste, Delete) must read safely.** `CommentEditSelectionTests.aStaleSelectionReadsClamped`; `CanvasTypingSelectionWindowTests.theKeysPublishWhatTheyDoBackToTheModel` deletes the whole text and keeps typing (Tasks 1 and 2).
4. **A multi-selection (a MetalUI value the editor never makes) must act on its first range, and an empty set must select nothing.** `CommentEditSelectionTests.aMultiSelectionReadsAsItsFirstRange` (Task 1).
5. **A second edit must open fresh, not where the last one ended, and Esc after typing over a selection must keep the old title.** `CommentEditSelectionTests.eachEditOpensWithItsOwnSelectionNotTheLastOnes`, `CanvasTypingSelectionWindowTests.eachEditOpensFreshNotWhereTheLastOneEnded`, `escapeAfterTypingOverASelectedTitleKeepsTheTitle` (Tasks 1 and 2).
6. **Not testable headless (human check C25-3, gap CT-d):** an input method composing while the title is all selected: the marked text must replace the selection, and the first Return of a composition must commit the composition, not the title.

```swift
import CreatorGraph
import Foundation
import MetalUI

/// A comment being typed into in place on the canvas (comments typing plan; spec 2026-10-09 §8): which comment, what it
/// held when editing began (Esc puts it back) and what has been typed since. View state: never undone, never saved.
/// The text reaches the graph only when the edit is committed (`EditorModel.commitCommentEdit()`), as one undo step.
public struct CommentEdit: Equatable, Sendable {
    public enum Kind: Equatable, Sendable {
        /// A note's multi-line text.
        case noteText
        /// A frame's single-line title.
        case frameTitle

        /// What a field of this kind selects when it opens on `text` (MetalUI C25, gap CT-b; spec 2026-10-09 §8 Errata
        /// (C25 adoption)): a title opens with all of it selected, as a rename does, so typing replaces it; a note
        /// opens with the caret at the end of its text, so typing appends.
        public func openingSelection(in text: String) -> TextSelection {
            switch self {
            case .frameTitle: TextSelection(range: text.startIndex..<text.endIndex)
            case .noteText: TextSelection(insertionPoint: text.endIndex)
            }
        }
    }

    public var id: CommentID
    public var kind: Kind
    /// What the note's text or the frame's title was when editing began.
    public var original: String
    /// What the field holds now.
    public var draft: String
    /// Names this edit's `PendingEntry`, so only the edit itself can replace or drop it, and the canvas view keys its
    /// field by it (a new edit is a new field, with focus asked for afresh).
    public var owner: UUID
    /// The field's selection: what it opened with (`Kind.openingSelection(in:)`), then what the field last published
    /// back (typing, a click, a double click, shift-arrows, ⌘A, delete). Its indices belong to the text the field held
    /// when it wrote them, so after the draft changes they may be stale; MetalUI reads a stale index safely and
    /// `selectedOffsets` clamps it. `nil` until set. It is not part of the undoable state and writes nothing to the graph.
    public var selection: TextSelection?

    /// The selection as Character offsets into `draft`, both ends clamped into the text (a stale index reads as the end).
    /// A multi-selection reads as its first range, which is the one the field acts on (MetalUI divergences 265, 266);
    /// `nil` when there is no selection.
    public var selectedOffsets: Range<Int>? {
        guard let selection else { return nil }
        let range: Range<String.Index>
        switch selection.indices {
        case .selection(let single): range = single
        case .multiSelection(let set):
            guard let first = set.ranges.first else { return nil }
            range = first
        }
        let count = draft.count
        func offset(_ index: String.Index) -> Int {
            if index <= draft.startIndex { return 0 }
            if index >= draft.endIndex { return count }
            return draft.distance(from: draft.startIndex, to: index)
        }
        let lower = offset(range.lowerBound)
        let upper = offset(range.upperBound)
        return min(lower, upper)..<max(lower, upper)
    }
}
```
